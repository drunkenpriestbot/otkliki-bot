# Пройденные ошибки и решения (читать перед сборкой)

Это конкретные грабли, на которые наступали при сборке точно такого же
пайплайна (мониторинг заказов → черновик отклика → уведомление), не абстрактные
советы. Если будешь собирать что-то похожее — не наступай на них снова.

## 1. Полная автоматизация откликов = риск блокировки аккаунта

На большинстве бирж фриланса (и в Telegram-чатах фрилансеров, если там действуют
похожие неформальные правила) автоматическая массовая отправка откликов
расценивается как спам/бот и ведёт к блокировке аккаунта или потере платных
"коннектов"/доступа к заказам. Рабочая схема — **полу-авто**: бот мониторит и
готовит черновик, отправляет человек сам, вручную, прочитав и при желании
подправив текст. Это полностью снимает риск блокировки и не требует обхода ToS.

## 2. Штатный `schedule:` в GitHub Actions — ненадёжен

На новых публичных репозиториях GitHub троттлит cron-триггер (`schedule:`):
вместо заданного интервала (например, 15 минут) реальный запуск происходит раз
в ~1.5-2 часа. Подтверждено замерами на практике, не теория.

**Решение:** убрать `schedule:` из workflow, оставить только `workflow_dispatch:`
(ручной/API-триггер — НЕ троттлится). Запуск дёргать снаружи через бесплатный
**cron-job.org** (без карты, только email): задание раз в N минут шлёт POST на

```
https://api.github.com/repos/<owner>/<repo>/actions/workflows/<workflow-file>.yml/dispatches
```

с телом `{"ref":"main"}` и заголовками:
```
Authorization: Bearer <fine-grained PAT>
Accept: application/vnd.github+json
Content-Type: application/json
```

PAT — fine-grained token, scope только на этот репозиторий, permission
`Actions: Read and write`. Создаётся в GitHub → Settings → Developer settings →
Personal access tokens → Fine-grained tokens.

## 3. `claude -p` "слипание" контекста между соседними вызовами в одном прогоне

Если в одном запуске скрипта несколько раз подряд быстро вызывать `claude -p`
(CLI) для разных независимых задач (например, написать черновик для заказа A,
потом для заказа B) — иногда ответ на один заказ примешивает контекст/детали из
соседнего заказа того же прогона, хотя это должны быть полностью независимые
запросы.

**Решение (всё вместе, проверено на практике):**
- Каждый вызов — из чистой временной рабочей директории (`tempfile.TemporaryDirectory()`),
  не из директории проекта — `claude -p` подхватывает историю сессий, накопленную
  для текущего cwd.
- Флаги `--no-session-persistence --session-id <случайный uuid>` — каждый вызов
  как новая сессия.
- Пауза `time.sleep(5)` между вызовами (не первым).
- В сам промпт добавлять nonce (случайный uuid) с явной инструкцией "это
  отдельный независимый запрос, игнорируй любой прошлый контекст".
- `--disallowedTools Read,Bash,Glob,Grep,WebFetch,WebSearch,Edit,Write,Task` —
  отключить инструменты, которые не нужны для текстовой генерации (не связано
  напрямую со слипанием контекста, но снижает риск побочных эффектов/затрат).

## 4. Двухступенчатый фильтр — дешёвый перед дорогим

Не отдавать Claude (тратит лимиты Pro-подписки или платный API) ВСЕ найденные
заказы на проверку релевантности — большинство будет явным мусором (не та
ниша/тематика). Сначала прогнать через **бесплатный** грубый фильтр (Groq API,
~1000 запросов/день без карты, понимает смысл, а не просто ключевые слова) —
и только то, что Groq сочтёт релевантным, отдавать Claude на финальную точную
проверку + написание черновика. Экономит лимиты на порядок без потери точности
(Claude всё равно делает финальную проверку, так что ложноположительные от Groq
не страшны — отсекутся на втором шаге).

## 5. Если Groq (или любой дешёвый фильтр) недоступен — не терять заказ молча

Если внешний API дешёвого фильтра упал/недоступен — пропускать заказ ДАЛЬШЕ
на следующий (дорогой, но надёжный) шаг, а не выкидывать его. Лучше потратить
лишний вызов Claude, чем незаметно потерять релевантный заказ из-за временного
сбоя стороннего бесплатного сервиса.

## 6. Формат уведомления в Telegram — code-block/blockquote вместо обычного текста

Черновик отклика в уведомлении должен быть оформлен как `<blockquote>` (HTML
parse_mode) — это даёт копирование одним тапом без обрезки. Кнопка
copy_text у Telegram-ботов ограничена 256 символами — для откликов длиннее
этого лимита она просто не сработает молча. Длинное описание заказа — в
`<blockquote expandable>`, чтобы не раздувать уведомление визуально, но
сохранить полный текст по тапу.

## 7. Редактирование черновика человеком после уведомления — отдельный вебхук

Если хочешь поправить черновик перед отправкой — проще всего Reply на
сообщение бота своим текстом. Чтобы не терять ссылку на заказ при этом,
отдельный бесплатный Cloudflare Worker (without карты, always-on, не требует
держать комп включённым) слушает Telegram webhook, видит `reply_to_message`,
достаёт ссылку на заказ из текста ИСХОДНОГО сообщения через regex и
прикрепляет такую же кнопку к отредактированному сообщению. Никакой базы
данных не нужно — ссылка и так есть в тексте оригинала.

## 8. Где регистрировать секреты и почему не в коде

Все токены/ключи — только как секреты GitHub Actions (Settings → Secrets and
variables → Actions) или секреты Cloudflare Worker (`wrangler secret put`),
никогда в коде или в коммитах. При работе с Claude Code (если используешь его
же для сборки бота) — попытки вписать токен прямо в shell-команду блокируются
защитным классификатором (credential leakage) — это ожидаемо и не нужно
обходить, штатный путь: `gh auth login` (логин через браузер) и
`gh secret set` для секретов репозитория.

## 9. Маркетинг-бриф/портфолио — статичный текст, без автосинхронизации

Данные о себе (УТП, портфолио, реальные цифры профиля) проще вшить как
статичный текстовый блок в промпт (`BRIEF`/`PORTFOLIO` в `draft.py`), который
обновляется вручную при изменении позиционирования, а не пытаться
синхронизировать в реальном времени с профилем на бирже/в канале — это лишняя
сложность без реальной выгоды, обновления происходят редко.
